# 来源投影与发布读取成本优化

本轮处理实际审查进程约1.3GB的内存开销，以及同一来源数据在审查/发布链路中的重复读取。没有更改来源、账号归属、指标、日期或采样规则。

## 找到的热点及修改

1. 全库有232个已完成来源任务，`request_json`合计176,259,570字符，单份最大约340万字符。旧补充来源投影把所有完整JSON一次取入JavaScript，再逐份解析后选择34份来源版本。
2. 新实现先通过SQLite逐条读取不含`rows`的元信息，仍由原来的`latestSources`算法比较来源键、修订和时间；只为选中的版本读取完整原始JSON。没有截断原始作者行或修改历史记录。
3. JSON顶层重复键、非法JSON及非数组`rows`仍走原始解析路径；不会用SQL“第一个重复键”的语义代替JavaScript原来的“最后一个键”。包含转义键名的反例已验证。原先会失败的顶层null仍明确失败，没有用空来源制造成功。
4. 文本脱敏原来对每段文字都遍历四千多个定位标识。现在每次读截面只构建一个有大小上限的字面量匹配器；不命中的文本直接跳过循环，命中的文本继续原来的顺序替换，保留重叠标识、替换标记、截断和凭据处理语义。无全局缓存，调用方数组后续变化不污染已建立的读截面。
5. 同一脱敏器用于账号分类、作品标题、来源文字与补充来源；没有减少隐私规则或把HTML/凭据检查移到可绕过的位置。匹配器无法构建或执行时回退原算法。

## 实库一致性证明

- 在同一个SQLite只读事务中，对比修改前后完整补充来源输出：**1,217,103字节逐字节一致**，含全部统计、作者、作品、观测、待关联记录与版本指纹。
- 同一事务对比当前账号分类投影：**4,130条、1,785,937字节逐字节一致**。
- 最终实库名册仍4944条，3936关联启用、49冲突暂停、959未关联，各分项与优化前一致。
- 原始内容没有复制到公开证据；公开保存哈希、字节数、记录数和测试结果。逐作者审查JSON仍只在私有目录，权限0600。

## 性能与运行观察

| 本机运行记录 | 优化前 | 优化后 |
|---|---:|---:|
| 完整名册审查独立进程耗时 | 12.82秒 | 4.36秒 |
| 同一命令最大RSS | 1,388,773,376字节 | 1,064,042,496字节 |
| 同一事务补充来源投影耗时 | 7.36秒 | 0.93秒 |

独立进程前后有后台负载差异，同进程测试有缓存效应；以上是本轮观察，不能作为跨机器速度承诺。优化后完整审查峰值仍约1GB，尚未达到低内存目标。没有把测试次数或性能改进写成新的平台采集覆盖。

现有发布器完成21:45:03Z的数据批次，并于21:54:47Z确认成功；随后两次状态核对确认无活动批次，现场确认旧PID存活才发送SIGTERM。原有launchd服务自动恢复，PID65106→75674，Nice10保持。采集主服务和来源worker未重启，没有创建第二个发布器或额外调度。

新进程确认仍引用相同成功批次、状态空闲。空闲RSS从约206万KiB回落至约11万KiB，这是重载后回收存量堆的观察，不证明内存泄漏已根治。新导出算法已由新进程加载，但下一次完整导出的峰值需自然批次继续验证；没有为跑分强制制造新发布或采集。

## 验证与限制
