# 入库审查列表的范围与翻页

审查积压超过2.5万条时，旧管理员接口始终返回最早20条，无法直接定位最近批次。真实接口一次读取约286ms，未发现足以据此声称“队列是主要性能瓶颈”的证据。本次修复的是新事件可达性和有界响应，不宣称全面提速或清空积压。

## 管理员接口

保留现有权限：`GET /api/ingestion-reviews` 仅管理员可用，查看者仍返回403。无查询参数时保持原响应和顺序：优先最早待审记录，再补已完成记录，同时给出最近5条已完成审查。

显式查询可以使用：

```text
?state=pending&order=newest&limit=20
?state=completed&order=newest&limit=10
?state=all&order=oldest&limit=50&afterRunId=27100
```

| 参数 | 含义 |
| --- | --- |
| `state` | `pending` / `completed` / `all`；显式查询默认`pending` |
| `order` | `oldest` / `newest`，按批次ID排序；默认`oldest` |
| `limit` | 每页1–100条，默认20 |
| `afterRunId` | 只取大于该批次ID的记录，不包含边界 |
| `beforeRunId` | 只取小于该批次ID的记录，不包含边界 |

显式查询返回`pagination`，包含本次条件、匹配数量、返回数量、`hasMore`和`next`。`next`仅含可直接放入`URLSearchParams`的筛选参数，保留另一侧边界，避免翻页时改变范围。末页`next=null`。重复参数、未知字段、非法顺序、反向边界、非安全整数及超过100条的请求，在扫描目录前返回400。

`totalPending`、`totalCompleted`始终是全队列的数量，不受筛选影响；`completedReviews`仍是全局最近5条。`status=empty`只表示当前选择没有记录，不能据此认定积压清空。旧原事件、完成凭证、名单、快照及数据库均不改写；读列表不会创建“已完成”审查。

## 不能混淆的边界

游标按批次ID，不是事件抵达顺序，也不是冻结快照。后来恢复的旧批次可能落在已读范围之外；检查迟到恢复事件仍需回看旧范围、全局待审列表和恢复队列，不能仅凭`afterRunId`声称看过所有新到事件。

所有完成凭证仍需通过原校验，分页不绕过未选中记录中的损坏凭证。没有按“看不到就算没有”隐藏积压，也没有将脚本规则审查冒充AI产品审查或真实用户留存试验。
