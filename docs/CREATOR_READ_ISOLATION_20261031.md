# 作者查询不再占用主服务事件循环

生产规模的单作者查询此前约需4.6秒。它不仅查一位作者，还同步构建统一作品集合、全局汇总、归属核验及采用值；与此同时发起的健康检查实测等待4219ms。CPU/SQL只读剖析确认存在全量读取和计算，不能通过只返回少数作品或减少核验冒充优化。

## 本次修改

- 将`/api/creator-operating-view`交给已有`ConsoleReader`串行只读工作线程，不新增线程池、采集任务、服务或调度。
- 返回原函数的完整结果，不经过列表精简投影。作者/作品、全局汇总、分类、时间范围、缺测、采用值及权限保持原契约。
- 此类读取不使用普通看板的30秒缓存，也不合并相同查询；同一截止时间下，外部新提交的来源或身份变化仍需重新核验。每次读取使用单一SQLite只读快照。
- 复用原有队列上限、包含排队时间的截止期限和请求取消；最后一位调用者断开时终止旧读取线程，确认释放后再服务排队请求。
- 在确认存在来源版本后，先检查发布日期范围，再构建全量数据。无效日期不再触发全库作品重算；没有来源时仍返回原来的`source_not_imported`。

## 实际验证

同一固定截止时间、同一查询、独立HTTP连接，生产前后完整响应逐字段一致：

| 测量 | 修改前 | 修改后 |
| --- | --- | --- |
| 作者查询耗时 | 4320ms | 4714ms |
| 查询发出100ms后启动的健康检查 | 4219ms | 1ms |
| 无效发布日期返回400 | 4017ms | 2ms |

这是单次现场测量，不是性能保证。有效作者查询的计算仍约4–5秒；本次解决的是主服务被阻塞以及无效筛选触发重算，不能声称作者查询本身已全面提速。共用读取队列的其他重查询仍可能等待。

源码和正式目录各11文件156项测试通过，含完整直接/线程结果一致、真实0、相同截止时间的新来源可见、无跨请求缓存、实际工作线程取消释放、HTTP断开、其他订阅者与排队任务、日期校验和历史归属回归。没有数据库业务写入、平台请求、浏览器采集或模型调用。

本次仅修改后端读取，不更改前端布局，不宣称完成浏览器/手机验收。全量作者关联、抖音逐作品点赞和实际每日发布完整采集，以及后续全量查询计算成本，仍需继续解决。
