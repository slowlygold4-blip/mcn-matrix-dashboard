## 先拆开作品归属对作者绑定的循环依赖

剩余作品检查显示：平台库存已有精确作品ID、原始发布者sec_uid及既有账号锚点，但当前strictPlatformPosts只搜索已进入来源作者绑定的账号。已知平台账号尚未绑定表内作者时，其真实作品会被漏过。这是作品索引与作者索引的循环依赖，不能通过伪造作者成功回执解决。

下一步先建立全体已知账号的作品发布者索引：精确作品ID、原生作者ID与账号canonical锚点、历史观察/发布时间全部通过后，发布者是已有账号实体；不依赖它先成为某个表内作者，也不把表内申报人自动绑定成该账号。原声明、待关联作者和实际发布账号分别保留在同一数据图中。账号原启停、板块和分类不改；注销账号的已核验历史作品仍可追溯，不能变成今日采样或今日零发布。原先的缺凭据问题与这项本地关联修复分开验收。

原作者列表、账号详情、作品查询、作者合计与发布台账必须采用同一账号实体键，避免只改总览、作者合计遗漏新实体。加入无来源作者节点的账号时，实际作品不丢失，原始来源作者不删除；只有后续独立身份回执通过后才收敛重复身份。再接入以下持久作者绑定流程。

## 落地顺序

1. 为身份关系建立追加式、带版本的来源绑定回执，引用现有原始快照而不复制大JSON。记录sourceSha/authorRowHash、target/canonicalID、snapshotID/sourceChecksum、auditID/runID、observedAt/committedAt和固定类型。幂等约束避免重复写入；新来源版本、目标变化或原行变化需重新核验。
2. 原总表与追加表调用同一个关联读取器。先保留已确认的一对一绑定，再处理严格的新候选；重复标识、别名歧义、跨作者目标争用、更新的生命周期或身份冲突均不能自动合并。
3. 在既有来源入库完成与主页采样审计提交后的路径上进行有界核对；处理两种先后顺序。沿用现有进程和调度，不新建周期任务，不调用模型，不重新抓取已有有效证据。
4. 原总表/追加表/统一名册/作者详情/导出/发布摘要/每日监控使用同一关系索引。缓存失效依据关系指纹；来源内容与发布时间分开，重用同一内容版本不会误报过期。
5. 新增身份回执若需要SQLite表，纳入一致性备份及还原计数；旧历史、原始名单、原始快照及原有回执不删除或覆盖。正式写入前先在临时小库验证，在只读真实数据上规划并独立复核，再通过产品现有入库事务执行。

## 验收

- 精确回放真实候选，说明新增关联和作者去重变化；旧绑定、启停、分类、历史指标和原始来源逐项不变。
- 矛盾SHA、错UID/sec_uid、未来记录、过期的新证据、更新的注销/身份冲突、错误run/audit、重复或重用的公开ID必须拒绝。
- 电脑离线后身份不会凭TTL消失；新的冲突会冻结当前采用并保留历史证据。缺测指标仍不补零，未采到作品仍不称未发布。
- 对同一来源连续处理不新增重复回执、不重复采集、不重复作者；失败无半成品入库。真实关联入库不等于作品已完整采集。
- 只交付通过真实读回的关联数量。当前抖音作品采集授权/403及全列表覆盖依然是另一个未解决的验收项。
