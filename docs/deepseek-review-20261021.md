# DeepSeek 改造任务书核对（2026-10-21）

结论：目标中的「播放来源可追溯、账号级健康、采集适配器可替换」值得做；所附代码和五天切换顺序不能直接执行。核对对象是本仓库 `134f6aa` 起的脱敏源码副本；本机 `server.mjs` 与 `public/rebuild.js` 的 SHA-256 与副本一致。基线 `npm test` 113/113。

## 已核对的事实

1. 当前路由 `/` 和 `/index.html` 指向 `rebuild.html`（`server.mjs` 的静态路由）；实际业务脚本是 `public/rebuild.js`。只重写 `public/app.js` 不会改变当前首页。
2. 当前 UI 已多处明确标注「估算播放 = 获赞净变化 × 100、非平台实际播放量」（`public/rebuild.html`、`public/rebuild.js`、`public/account-detail.js`）。不过作品历史另有「来源播放字段」；它被标为未独立核验，抖音返回 0 时还提示可能为占位。新三态契约可进一步统一，但不能把所有旧来源字段自动升格为 `api` 实际播放。
3. 采集链路确实复杂，`lib/providers/public-web.mjs` 引用四个脚本；但现有服务已经有 `lib/providers/index.mjs` 抽象、两个分开的主页/作品覆盖维度、账号状态详情和作品错误原因分布。声称「6 类错误完全不可见」不准确；真正缺口是账号列表首屏没有持续失败次数与稳定错误码。
4. Node 24 门槛不是单改 `package.json` 可解除：`lib/database.mjs`、读 worker 等使用 `node:sqlite`，官方文档显示该模块在 Node 22.5.0 才加入。要支持 Node 18，必须替换存储实现或让 `npm start` 明确启动另一套已安装的服务，再独立验证全部功能。

## 所附代码不能直接上线的原因

- `config.yaml` 放两个示例账号并创建新的 `data/monitor.db`，没有将现有账号、历史快照、板块、话题、权限、来源证据迁移；直接切换会表现为大量数据「消失」。示例账号不得充当真实监控对象。
- 新 FastAPI 样例绑定 `0.0.0.0`，`POST /api/trigger` 无认证、限流或防重复，任何可达网络的访问者都能重复启动采集；还取消了现有团队权限边界。
- 响应事件回调内部抛出的 401/403/429 异常不可靠地传播到 `collect()`；`_check_login()` 的弹窗选择器可能把公开页面误判成必须登录。应在受控任务中收集错误并在主采集协程抛出。
- `pw-stealth-enhanced` 与 `--disable-blink-features=AutomationControlled` 属反检测措施，不应当作访问受限时的默认解法；遭拒绝、限流或验证码时应记录状态并停止该路径。
- `save_videos()` 与 `save_profile()` 分开提交并各自取时钟；崩溃可留下半次采样，`summary` 会把最多 30 条作品的点赞或播放汇总误称为账号总量。缺失的点赞/评论也被 `or 0` 写成零。
- `summary.total_plays` 只要某一条作品有数字就相加，混合缺测与采样截断，容易形成虚假的「总播放」。应在契约中明确样本范围、覆盖率；未证明全量时账号总播放保持 `null`。
- `main.py` 直接实例化 `DouyinPublicProvider`，新增一个 provider 文件仍须改主程序；未达到「服务层与前端零改动」。
- `npm start` 在 Node 18 下仍指向旧 `server.mjs`，不能通过调低 `engines` 验收。

## 纠正后的迁移门槛

1. 先固定真实数据语义：`plays=null` 表示缺测；`plays_source` 只允许 `api/estimated/unavailable`，`api` 必须有可验证的响应来源和作品身份，`estimated` 仅作单独估算，任何区间或账号总量都不得混合三态。作品样本和账号全量分开。
2. 先在现有体系增补账号级错误码与连续失败计数，并在实际入口 `rebuild.js` 显示；维持主页/作品/话题独立覆盖。此项已在本分支实现；隔离库迁移、错误累积/复位、前端呈现和全套 120 项测试通过，但尚未部署到正式服务或正式数据库。
3. 如果需要 Python provider，先做影子采集：从经授权的现有名册只读取得目标，写入隔离库，不覆盖旧库；按账号核对身份、采样时间、三项主页指标和作品样本，再评估切换。依赖仅保留正常浏览器会话，不自动绕过拒绝或验证码。
4. 新服务至少要复刻现有认证、CSRF/同源、防并发、名单导入、分类、话题、历史对比和备份能力。公开只读服务与管理写入服务继续隔离。满足相应测试和临时副本恢复演练后才切流、退役旧脚本。
5. Node 18 是单独的兼容工程，不与采集器替换混成一个版本号改动。保留旧入口直到替代服务的启动、恢复、权限和数据一致性验收全部通过。

本审查未在正式数据库上迁移或采集；不宣称新 FastAPI/Playwright 链路已跑通，也不宣称 Node 18 已兼容。
