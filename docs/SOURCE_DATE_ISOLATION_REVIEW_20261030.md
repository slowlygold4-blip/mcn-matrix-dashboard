# 作品原表日期读取与保留审查

## 问题及修改

日常验收仍为：粉丝及日变化、每条作品点赞及日变化、账号总获赞及日变化、每日是否发布和发布数量。主页请求成功不能证明作品采样完成。

原作品表读取器在发布日期或统计日期无效时抛出行级异常，连同独立有效的作品 ID、作者标识、点赞和播放字段一起丢弃。六组回归先复现失败；另有一组兼容性回归在修改前已通过。旧测试还把“坏统计日期导致整行丢弃”作为预期，现按字段隔离要求纠正，保留作品身份、数值和原日期内容的断言。

现在只将有问题的日期置为未知，在该事实中保存 `dateIssues` 和 `rawDateValues`。不填入发布时间、导入时间或当前日期，不将未知点赞变成 0，也不把来源事实改写成平台采样。无效或冲突的作品身份仍按原规则隔离；这次修改没有放宽账号归属规则。

日期读取支持明确的年在前日期、带时区的完整时间和原单元格声明为日期格式的 Excel 数值；带时区时间转为北京日期，Excel 1900/1904 日期系统分别处理。无格式的纯数字、月日在前的歧义文本、只有时分的格式、没有时区的时间文本及 Excel 虚构的 1900-02-29 保持未知。日期字段仍是日期精度，没有生成虚假的具体观测时刻。

## 验证与发布

- 共 193 项相关后端回归通过，覆盖原表读取、事实事务、幂等、来源轮询、归属、统一作品及公开投影；在正式后台目录同组通过，两次不是 386 项独立测试。
- 对正式库四份原始文件重新解析，共 28,396 行事实。四份原件、事实集合和报告的 SHA256 均与已保存版本完全一致；原有有效事实形状保持兼容，没有为解析器升级覆盖原版数据。
- 最新一致性备份通过临时硬链接只读打开，`quick_check=ok`，四个来源事实表计数与备份清单一致；没有额外复制整库。
- 使用原来源轮询互斥锁确认无在途来源读取后，更新解析器并重载已有来源进程；主服务和公开发布器保持原进程，没有新增定时任务或重复采集。未修改前端，本阶段无需发布新 Site 版本。
- 本轮业务数据库写入为 0。现有四份来源没有因错误日期被整行丢弃的记录，因此不能声称这次凭空恢复了某个数量的历史作品。修复适用于后续来源读取，不改写不可变旧版本。

## GitHub 方案核查及真实采样结果

使用 Agent Reach 的 GitHub CLI 路由读取固定提交，不安装或执行外部仓库脚本：

1. [anbeime/skill 的作品提取脚本](https://github.com/anbeime/skill/blob/dd37b9d94f94366b4a31b2584e69b1fc596e1199/skills/viral-video-copywriting/viral-video-copywriting/scripts/extract_douyin_video.py) 在只取得 HTML 标题时也会返回成功并把缺失点赞等指标写为 0；不符合本产品缺测规则，未采用。
2. [Python3-Spider 的公开作品解析](https://github.com/wkunzhi/Python3-Spider/blob/5188ca4056bb94d956df9ddbeb42c765ebe9819a/%E3%80%90%E6%8A%96%E9%9F%B3%E3%80%91%E6%97%A0%E6%B0%B4%E5%8D%B0%E8%A7%86%E9%A2%91%E8%A7%A3%E6%9E%90/parse.py) 展示旧版 `iesdouyin` iteminfo 读取；对库中一个已知作品仅做一次匿名 HTTP 试验，返回 200、JSON 类型但正文 0 字节，没有作品指标。未重试或批量扫描，也未接入生产采样。

上述试验不启动抖音浏览器、不读取登录态、不处理验证码、不调用模型，不写数据库。已有分享页探针的“200 但作品数组为空”也不能作为采样成功。

**抖音当天单作品点赞观测缺口仍未解决。** 本阶段是修复来源数据保留和日期读取，不宣称全量每日采集恢复、完整发布数量已知或全部作者都完成监控。继续需要可验证的作品级数据读取与每日覆盖证据。
