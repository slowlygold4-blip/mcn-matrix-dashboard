# 原表 UID 与作者别名归并 — 2026-10-30

## 实际问题

原始作品表明确提供作者UID，但总表的“账号标识”列可能同时包含UID、短号或公开抖音号。此前只按公开抖音号匹配，并限制一个监控账号只能对应一条来源作者行。同一人的UID行、旧抖音号行和当前抖音号行因此被留成多个作者，部分原表作品也没有回到已有账号。

固定只读核查找到5条这类来源资料，均对应现有监控账号。它们来自4481行的基础作者表；这个范围不等于全部来源作者或当前启用监控账号数。

## 实现

1. 复用原表明确的作品ID、作者UID和物理行哈希，结合已保存的官方主页、审查回执与run证明进行交叉核验。UID、短号、公开抖音号分开处理，不按昵称猜归属，不发额外平台请求。
2. 关联以版本2身份回执追加到已有表。原作者行、原作品行、原件、指标、启停和人工修正不改写；保留实际准入时间，不把今天确认的关系回填到过去的知识截面。
3. 同一账号允许多条经过核验的来源别名，保留一个主作者行。作品按ID只计一次；姓名、分类、登记证据和原账号标识保留。普通双重身份声明仍视为歧义，错误的主行指针不能挤掉已有有效关联。
4. 过期离线不删除已准入身份。新主页UID矛盾、原表明确的新UID矛盾、重复UID目标、原件或回执损坏、人工身份更正会阻止当前使用；单纯从新表删除作品不等于平台删除或身份撤销。
5. 原表UID证据只在其原始来源关系内使用，不将该数字当成另一张表的公开抖音号。跨来源ID碰撞仍需要各自的身份语义和证据。
6. 单账号完成钩子先做轻量候选检查，没有候选不重读整套作品。实库只读测量：全量候选计划约584ms；一个无候选微批次约9ms，实际值随机器负载变化。

## 真实数据验证

- 选择性内存演练中，原表关联行3660→3665；基础作者投影4481→4476，5条重复标识归并到原账号。
- 18179个来源作品的ID、日期、累计点赞和累计播放全部保留；原来源行及目标字段不变，正式库写入0。演练曾因复制历史范围偏大达到约3.8GB内存，进程已退出；后续正式校验使用流式散列，不重复复制这些历史。
- 正式加载后，身份回执4→9，旧4条哈希保持；5条新回执已实际入库。原表34150行、4份作品来源版本、板块及4134目标用户字段保留。两次自然采样更新的核验时间单独追查，不把它们误报为人工字段修改。
- 本机API用5个原标识均可查询到唯一对应作者及合并作品。API当前约4秒的读取耗时仍需优化，不能称交互性能已经达标。

## 公开发布契约与失败恢复

公开目录保持一个账号对应一个主作者行。原别名行只在源数据和追溯关系中保留，不重复发成公开目录账号。兼容字段`reciprocalDuplicates`按契约统计所有已确认并移除的重复作者行，包括UID别名；`rawAuthorRows`仍是原始行数。

实际发布曾拦截三个未上传的草稿：一个来自更新前已启动的导出任务，包含重复目标目录；另一个暴露旧重复计数等式没有包含UID去重；第三个暴露补充来源索引仍沿用去重前的基础作者数，未通过与作者索引的交叉校验。三份失败控制记录已保存，未覆盖公开旧版。

补充来源索引现在复用相同的已验证UID别名投影计算基础作者数，同时保留原标识用于补充来源匹配，避免被去重的别名又成为“新增作者”。新增完整作者分区类型验证、总量/指纹审查和作者/补充来源联合回归；真实草稿的22个作者分区、18179作品以及补充来源129作者、108作品、3884观测的交叉审查均已通过。源码和正式目录各33文件337测试通过。公开新批次是否已激活仍以实际回读为准。

`retireUnsentPreparation`只生成恢复提案。必须先停止受管发布器，并满足：错误发生在校验阶段、无上传/激活尝试、检查点仍属于前一已激活版本、匿名云端清单与旧检查点及本机普通来源分区一致。恢复前保存失败控制记录，保留旧草稿，不修改业务数据库。摘要分区是同步时派生的清单，单独按已公开检查点校验，不能拿原始导出清单逐字相等代替这一层验证。上传、激活或回读阶段的不确定失败不能按此办法退役。

同时，身份回执单独新增会改变发布标识，不再要求必须等一轮账号采样或来源版本变化才发现关联更新。实际激活与匿名回读证据保存在私有维护日志；测试通过和本机API成功均不能替代公开验收。

## 仍未完成

抖音全作品采集和四项日常完整覆盖尚未恢复。公开端按旧别名搜索的交互、主页覆盖口径及API读取性能仍需接续审查；本轮没有界面或手机验收，不把这些源数据关系修复称为完整产品完成。
