# 作者身份时序与原始快照留存审查

## 已修复的实际错误

`lib/profile-identity-proof.mjs`接受UTC时间有/无毫秒两种形式，但按文本降序选择最近快照、审核和生命周期事件。同一秒内，`...00Z`会排在更新的`...00.001Z`前。可使较新无效快照、较新拒绝审核或较新身份状态变化被旧的有利证据遮蔽。

三个回归用例在旧实现均失败，最终实现均通过；三处查询改为按实际时间`julianday`排序，同一时刻再以id决定先后。原校验和、原始资料、UID/sec_uid、审核/批次、24小时新鲜度、暂停和冲突条件不放宽，不生成绑定回执或采样记录。

## 减少不必要的内存留存

`lib/roster-alias-history.mjs`扫描当前账号发现候选时，旧Map保存所有完整raw快照直到历史事件检查结束。改为只保留不可变snapshot id；事件经过初步校验后再取对应原始行。仍完整解析原始JSON，重复键/异常结构等语义未更换，也未跳过验证。

1000个合成账号、每账号128KiB原始payload的独立进程观察：旧最大RSS423040KiB，新241840KiB；读取后RSS约433MB→246MB，时间94→91毫秒。仅为此合成场景的单次观察，不代表线上整个服务或全名册审查的内存已降低同一比例。

尝试过SQLite JSON字段投影方案，但实库读取反而更慢（主页身份416→895毫秒，别名112→338毫秒），已撤回本轮该方案及新建helper，最终未发布。没有为了性能跳过歧义、重复键、异常JSON或原证据验证。
