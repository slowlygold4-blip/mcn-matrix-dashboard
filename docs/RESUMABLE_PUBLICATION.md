# 可接续的全量历史校验

## 真实问题

公开发布有上万分区。上传完成后，旧实现把四千多个账号日历史与日期索引的全量核验放在同一HTTP激活请求中。生产日志曾记录该请求约110秒后被取消；上传成功因此不代表公开数据已经切换。既有上传断点不能保存该请求内部的校验进度。

## 实现

沿用同一个发布进程、上传断点和生产者权限，不增加调度或采集任务。上传完成后，发布器以 `audit-date` 请求按固定256个日历史分区分批核验。每一批仍读取并验证日期索引及其全部日期分片，再对本批的每一个原始日历史校验字节、SHA、记录数、目标身份、日期、指标向量及摘要对应关系。没有把少量抽查改称全量验证。

一批完整通过后，由服务器在私有R2前缀 `__replica_date_audits/v1/` 记录无业务明细的证明。证明绑定完整清单SHA、精确代际、固定协议、批次边界和数量，普通上传路径不能写入该前缀。客户端不能自行声明完成；断网后重试只复用精确匹配的服务器证明。缺批、伪造字段、清单改变或原始数据校验失败均不能通过。

最终 `activate` 先复核数据库中的全部分区元数据与清单一致，再要求所有日期核验证明齐全。历史汇总、作品发布索引、作者作品、补充来源及原生归属证据依旧逐项核验，全部通过才提交公开代际。任何失败保留之前公开数据。旧调用方仍可使用原单请求全量校验。

源分区内容以SHA寻址，生产接口禁止同一代际分区哈希变更；各批证明在此不可变契约下有效。运维人员直接在对象存储中篡改或删除已经验证的对象不属于这一接口的正常写入路径；读端原有字节/SHA核验继续保留。

## 验证与边界

- 合成SQLite/D1/R2接口测试覆盖513账号分三批、重复请求、缺批、伪造/跨清单证明、校验失败与恢复、未授权请求、无效批次和旧调用方。
- 发布器测试覆盖途中失败保留全部上传断点、恢复不重复上传、错误确认不能激活、固定错误码脱敏。
- 使用真实封存日历史生成对应日期索引，在本地把4126个原始分区分为17批逐一验证；证明存在时重复校验不再重读来源。该步骤没有网络、业务数据库写入或模型调用，不能代替生产网络验收。
- 原生部署成功也不等于当前数据发布成功。须接续原发布进程，查看实际 `source-audit` 批次与最终公开分区回读。

本修复改善已采数据的发布稳定性，不能填补抖音单作品每日点赞和完整每日发布采集缺口；四项日常采集仍需分别验收。
